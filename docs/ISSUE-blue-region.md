# 已知问题：画面左下角出现蓝色区域

**状态**：未解决，已排除多个假设，需要换思路
**发现时间**：2026-11-12
**影响**：视觉瑕疵。玩家在野外（如神山 z≈90）时，画面左下角有一片纯蓝色区域，
        边缘是一条笔直的斜线，看起来像"地面破了个洞露出海水"。
        不影响操作与性能，但明显破坏画面。

---

## 现象

```
位置：玩家在 (0, 90) 附近（神山山脚）时，画面左下角
外观：一片纯蓝色（#7AB7CE），无草纹理、无阴影，边界是一条直斜线
占比：约 8.8% 的屏幕像素
稳定复现：是
```

复现命令：
```bash
node tools/shot-natural.js 0 90 out.png 2000
```

## 唯一确定的线索（自相矛盾）

**只渲染地面块**（隐藏其余 278 个场景对象）时，该处的采样值是**清屏色**：

```
基线            : rgb(122,183,206)  (蓝色)
只留地面+洋红清屏: rgb(255,0,255)   (洋红 = 该处没有几何体)
```

**但**从同一个屏幕点发射线，`raycaster.intersectObjects(G.world.ground)` **能命中地面块**（距离 22）。

raycast 基于 CPU 的几何体求交，不经过光栅化；渲染走 GPU。两者结论矛盾，
说明问题出在**光栅化阶段**，而不是几何数据本身。

## 下次的建议排查方向

### 方向 1：WebGL 线框模式（最推荐）

直接看该处的三角形实际形状，判断是：
- 三角形不存在（几何问题）
- 三角形存在但被剔除（winding / cull face 问题）
- 三角形存在但被深度测试丢弃（depth 问题）

```js
// 在页面控制台执行
G.world.ground.forEach(m => {
  m.material.wireframe = true;
  m.material.needsUpdate = true;
});
```

### 方向 2：逐个地面块的二分法（要改诊断方法）

之前的 `_diag-whodraws.js` 逐个隐藏 301 个对象，每次都完整渲染 + 读回像素，
导致 CDP 超时。改进方法：
- 只隐藏 37 个地面块（不是 301 个）
- 用 `readPixels` 只读 1 个像素（不是整帧）
- 或用 WebGL 的 `gl.readPixels` 直接从 GPU 读，跳过 three.js 封装

### 方向 3：检查是否与"重叠块"有关

我在 `W.build()` 里给地面块加了 4 单位重叠（`OVERLAP = 4`）以避免接缝。
重叠加 `mesh.position.y += (tileCount % 7) * 0.02` 的 Y 偏移，
可能在某些角度产生**深度冲突**，导致后画的三角形被前画的覆盖后
又因深度测试失败而整片丢弃。

**验证方法**：把 `OVERLAP` 设为 0，`position.y` 偏移设为 0，看蓝色是否消失。

### 方向 4：检查 `art.grassTexture` 的 repeat 与 UV

`buildGroundMesh` 里 `repeat: 8`，而块的实际尺寸是 68×68（含重叠）。
如果 UV 计算有误，可能某些三角形采样到贴图外的空白区域。
但贴图有 `RepeatWrapping`，理论上不该出现纯色。

## 排查耗时记录（教训）

这个问题投入了约 15 轮排查，每个假设都被数据推翻。

**主要教训**：
1. **每次都完整渲染 + 读整帧像素**作为验证手段，太慢且容易超时，
   应该只读单个像素。
2. **多个假设互相独立地失败**时，应该怀疑"验证方法本身有问题"，
   而不是继续列举新假设。实际我犯的错是：用 `readRenderTargetPixels`
   读 outputRT，但 outputRT 是后处理结果，可能经过了描边叠加，
   颜色和 sceneRT 不完全对应。
3. 应该**先做线框可视化**（方向 1），那是唯一能直接看到真相的手段，
   而不是一直用间接的颜色采样去推断。
